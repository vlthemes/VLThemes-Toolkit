Задача: разработать собственный Visual Portfolio / Grid Builder внутри VLThemes Toolkit
Ты работаешь с существующим WordPress-плагином VLThemes Toolkit. Необходимо изучить его текущую архитектуру и реализовать полноценный модуль Portfolio / Grid Builder, функционально вдохновлённый Visual Portfolio, но разработанный самостоятельно.
Это не отдельный плагин и не внешний проект. Это новый самостоятельный модуль внутри существующего VLThemes Toolkit.
1. Обязательное расположение файлов
Весь код Grid Builder должен находиться строго в каталоге:
VLThemes-toolkit/includes/grid-builder/
Пример рекомендуемой структуры:
VLThemes-toolkit/
└── includes/
    └── grid-builder/
        ├── grid-builder.php
        ├── post-types.php
        ├── query-builder.php
        ├── layout-engine.php
        ├── skin-manager.php
        ├── shortcode.php
        ├── ajax.php
        ├── assets/
        │   ├── css/
        │   └── js/
        ├── layouts/
        │   ├── grid/
        │   ├── tiles/
        │   └── masonry/
        ├── skins/
        │   ├── Default/
        │   └── Fade/
        ├── admin/
        └── ...
Это рекомендуемый пример: адаптируй названия файлов и внутренние подпапки под реальную архитектуру проекта, если это необходимо. Однако вся реализация модуля должна оставаться внутри includes/grid-builder/.
Обязательные правила:
* Не создавай отдельный WordPress-плагин.
* Не выноси функциональность модуля в другие каталоги VLThemes Toolkit.
* Не размещай реализацию в plugins/, themes/, src/ или других каталогах за пределами includes/grid-builder/.
* Интегрируй модуль через существующий главный файл VLThemes Toolkit и его механизм подключения классов и файлов.
* Сначала изучи, как в проекте организованы загрузка модулей, автозагрузка классов, хуки, настройки, админка и подключение CSS/JS.
* Если в проекте используется require_once, существующий bootstrap или autoloader, следуй принятому подходу.
* Используй корректные пути к файлам и URL относительно расположения модуля.
* Не используй жёстко заданные абсолютные пути файловой системы.
* Не создавай параллельную инфраструктуру, если аналогичные механизмы уже существуют в VLThemes Toolkit.
2. Главная цель
Создать независимую систему создания портфолио и сеток контента с возможностями:
* Создание и управление элементами портфолио.
* Собственные категории и теги портфолио.
* Создание и сохранение конфигураций сеток.
* Gutenberg-редактор конфигурации.
* Query Builder для выбора источника контента.
* Layout Engine с режимами Grid, Tiles и Masonry.
* Система скинов с автоматическим обнаружением.
* Фильтрация элементов через AJAX.
* AJAX-пагинация и Load More.
* Собственный CSS для каждой сохранённой сетки.
* Шорткод для вставки сохранённой сетки на любую страницу.
* Адаптивность и возможность расширения функциональности.
Ориентируйся на удобство и возможности Visual Portfolio, но создай собственную реализацию. Не копируй его исходный код, внутреннюю архитектуру или защищённые материалы и не подключай Visual Portfolio как зависимость.
Все функции должны работать в контексте существующего VLThemes Toolkit.
3. Перед началом реализации
Сначала изучи реальный код проекта.
Проверь:
1. Главный файл плагина и порядок загрузки модулей.
2. Структуру includes/.
3. Используемые пространства имён, классы, префиксы и соглашения об именовании.
4. Способ регистрации CPT, таксономий, настроек и административных страниц.
5. Существующие компоненты Gutenberg.
6. Механизмы подключения скриптов и стилей.
7. Наличие AJAX-обработчиков, REST API, helper-функций и других пригодных компонентов.
8. Поддерживаемую версию WordPress и PHP, насколько это можно установить из проекта.
Перед изменением файлов кратко представь план реализации и перечень файлов, которые предполагается создать или изменить.
Затем приступай к реализации. Не ограничивайся планом, демонстрацией интерфейса или заглушками.
4. Типы записей
4.1. Portfolio Items
Создай Custom Post Type для элементов портфолио.
Предусмотри:
* Заголовок.
* Основное содержимое.
* Миниатюру записи.
* Галерею или дополнительные изображения, если это необходимо для выбранной архитектуры.
* Собственные категории портфолио.
* Собственные теги портфолио.
* Поддержку стандартных возможностей WordPress, необходимых для работы в редакторе и Query Builder.
* Возможность расширения дополнительными метаданными.
Категории и теги портфолио должны быть отдельными таксономиями и не должны смешиваться со стандартными категориями и тегами записей блога.
Настрой тип записи так, чтобы она корректно работала в админке WordPress и могла использоваться как источник для сеток.
4.2. Saved Layouts
Создай отдельный Custom Post Type для сохранённых конфигураций сеток.
Каждая сохранённая конфигурация должна содержать:
* Query Builder settings.
* Тип макета.
* Настройки колонок и размеров.
* Настройки адаптивности.
* Настройки фильтров.
* Настройки пагинации.
* Выбранный скин.
* Параметры отображения карточек.
* Пользовательский CSS.
* Другие параметры, необходимые для полного восстановления макета.
Храни конфигурацию в структурированном виде, предпочтительно в post meta с валидацией и совместимым форматом данных.
Сохранённая конфигурация должна полностью восстанавливаться при повторном открытии редактора.
Изменение одной конфигурации не должно случайно менять настройки другой.
5. Gutenberg-редактор Saved Layouts
Создай удобный редактор настроек сетки внутри записи Saved Layouts.
Если в проекте уже есть подходящая инфраструктура Gutenberg, используй её. Если нет, реализуй необходимый интерфейс совместимым способом.
Раздели настройки на логические панели или вкладки:
1. Query Builder.
2. Layout.
3. Responsive.
4. Filters.
5. Pagination.
6. Skin.
7. Card Settings.
8. Custom CSS.
Требования:
* Все поля должны сохранять свои значения.
* Настройки должны корректно загружаться при повторном открытии.
* Изменения должны сохраняться штатным способом WordPress.
* Проверяй и валидируй входные данные.
* Для полей, где это удобно, используй выпадающие списки, переключатели, числовые поля и понятные подписи.
* Не создавай декоративные элементы управления, которые ничего не делают.
* Не используй фиктивные кнопки и статические демонстрационные данные вместо рабочей функциональности.
По возможности предусмотрите предварительный просмотр макета. Если live preview реализовать без чрезмерного усложнения нельзя, сначала обеспечь полную работоспособность сохранения и рендеринга.
6. Query Builder
Реализуй полноценный Query Builder, определяющий, какие элементы выводятся в сетке.
Источники данных
Предусмотри возможность выбора:
* Обычных записей WordPress (post).
* Элементов портфолио (portfolio или фактический slug созданного CPT).
* Страниц (page).
* Других зарегистрированных публичных Custom Post Types.
* Изображений из медиатеки WordPress.
* Дополнительных источников через расширяемую архитектуру.
Не отображай несуществующие или недоступные источники. Для CPT формируй список на основе реально зарегистрированных типов записей.
Для источника изображений из медиатеки реализуй корректный запрос и адаптированный рендеринг. Не предполагай, что каждый источник обязательно содержит обычную запись с одинаковым набором полей.
Параметры запроса
Поддержи:
* Количество элементов на странице.
* Сортировку (ASC, DESC).
* Сортировку по дате, заголовку, ID, меню, случайному порядку и другим разумным поддерживаемым значениям WordPress.
* Исключение конкретных записей.
* Фильтрацию по категориям и тегам.
* Фильтрацию по выбранным таксономиям.
* Выбор нескольких терминов.
* Смещение (offset), если оно совместимо с выбранным режимом пагинации.
* Поиск по строке, если это предусмотрено интерфейсом.
* Поддержку расширения через фильтры WordPress.
Параметры должны валидироваться. Не передавай произвольные значения пользователя непосредственно в запросы без проверки.
Если комбинация offset и пагинации создаёт неоднозначное поведение, зафиксируй и реализуй предсказуемые правила.
7. Layout Engine
Создай единый Layout Engine, который принимает результаты Query Builder и выводит их в выбранном формате.
Минимально необходимые типы макетов:
* Grid.
* Tiles.
* Masonry.
Каждый тип макета должен иметь отдельную логику построения разметки и настроек, но использовать общую систему запросов, карточек, скинов и пагинации.
Не дублируй целиком одну и ту же логику рендеринга в каждом макете.
7.1. Grid
Реализуй классическую сетку.
Настройки:
* Количество колонок на больших экранах.
* Количество колонок на планшетах.
* Количество колонок на мобильных устройствах.
* Горизонтальный отступ между элементами.
* Вертикальный отступ между элементами.
* Соотношение сторон изображения.
* Поведение изображения: cover или contain, где применимо.
* Выравнивание и базовые настройки карточки.
Пример:
Desktop: 4 columns
Tablet: 2 columns
Mobile: 1 column
Horizontal gap: 24px
Vertical gap: 24px
Image ratio: 4:3
Значения должны настраиваться в редакторе. Приведённые параметры являются только примером.
7.2. Tiles
Реализуй отдельный режим Tiles, позволяющий создавать композиции из элементов разного размера.
Нужен редактор композиции или понятное текстовое представление схемы.
Пример синтаксиса:
3|1,.5;2,1
В этом примере:
* 3 — количество колонок композиции.
* 1,.5 — первый тип элемента занимает 1 колонку и имеет высоту 0,5 условной единицы.
* 2,1 — второй тип элемента занимает 2 колонки и имеет высоту 1 условную единицу.
Это пример пользовательского формата, а не существующий стандарт. Определи и задокументируй его грамматику.
Требования:
* Создай парсер конфигурации Tiles.
* Проверяй синтаксис и допустимые значения.
* Показывай понятные ошибки в редакторе при некорректной конфигурации.
* Реализуй повторение шаблона композиции для последующих элементов.
* Корректно обрабатывай последнюю неполную группу элементов.
* Не допускай отрицательных размеров и невалидных значений.
* Поддержи адаптивное поведение для мобильных устройств.
* Если исходная композиция не подходит для узкого экрана, используй предсказуемую перестройку размеров или количества колонок.
Если формат композиции требует неоднозначных правил размещения, сначала определи их явно и затем реализуй единообразно.
7.3. Masonry
Реализуй Masonry без сторонних библиотек.
Используй только CSS для раскладки Masonry. Предпочтительный подход — CSS Columns, если он совместим с требованиями к разметке и производительности.
Запрещено:
* Подключать сторонние Masonry-библиотеки.
* Использовать JavaScript для расчёта координат элементов.
* Позиционировать элементы с помощью вычисления top и left.
* Создавать собственный JavaScript-layout engine для распределения карточек по колонкам.
Учитывай особенности CSS Columns: визуальный порядок может идти сверху вниз по колонке, а не слева направо по строке. Это поведение необходимо принять осознанно и не маскировать под обычный Grid.
Обеспечь корректную работу с адаптивностью, изображениями разной высоты и динамически загружаемыми элементами.
8. Система скинов
Создай расширяемую систему скинов.
Пример структуры:
includes/grid-builder/skins/
├── Default/
│   ├── skin.php
│   ├── style.css
│   └── script.js
└── Fade/
    ├── skin.php
    ├── style.css
    └── script.js
Структура отдельного скина может быть изменена в соответствии с архитектурой проекта, но все встроенные скины должны находиться внутри includes/grid-builder/skins/.
Автоматическая регистрация
Система должна автоматически обнаруживать доступные скины в предусмотренных каталогах.
Не требуй вручную редактировать центральный массив при добавлении нового скина.
Каждый скин должен предоставлять необходимые метаданные, идентификатор и механизм подключения ресурсов. Используй безопасный механизм обнаружения и регистрации.
Предусмотри WordPress-фильтры, позволяющие другим разработчикам регистрировать дополнительные скины.
Начальные скины
Создай как минимум:
* Default — базовый, нейтральный скин.
* Fade — скин с эффектом плавного появления или перехода при наведении, если это соответствует дизайну карточек.
Скины должны реально отличаться визуально, а не просто иметь разные названия.
Требования
* CSS и JS скина загружаются только там, где они действительно необходимы.
* Не подключай все ресурсы всех скинов на каждой странице.
* Используй уникальные идентификаторы экземпляров сетки.
* Стили одного скина не должны случайно влиять на несвязанные элементы сайта.
* Проверяй корректность имени скина перед подключением файлов.
* Не позволяй произвольным пользовательским значениям превращаться в пути для подключения файлов.
Иерархия переопределения
Предусмотри возможность переопределять встроенные скины через тему WordPress.
Рекомендуемая иерархия поиска:
1. Дочерняя тема.
2. Родительская тема, если это применимо.
3. Встроенный каталог плагина.
Для переопределений используй отдельную документированную структуру каталогов внутри темы, например:
your-theme/
└── VLThemes-toolkit/
    └── grid-builder/
        └── skins/
            └── Fade/
                ├── skin.php
                └── style.css
Сначала проверь, нет ли в VLThemes Toolkit уже принятого механизма переопределения шаблонов, и при наличии используй его.
Не изменяй встроенные файлы скинов автоматически и не требуй редактирования файлов плагина для настройки дизайна.
9. Пользовательский CSS для каждой сетки
В редакторе Saved Layouts добавь поле Custom CSS.
Пользователь должен иметь возможность написать CSS для конкретной сохранённой сетки.
Например:
selector .title {
    color: red;
}

.portfolio-item {
    border-radius: 12px;
}
Требования:
* CSS должен применяться только к экземплярам соответствующей сохранённой конфигурации.
* Он не должен случайно менять другие сетки на той же странице или элементы сайта.
* Предусмотри уникальный контейнер для каждой сетки.
* По возможности поддержи написание обычных CSS-селекторов без обязательного ручного указания уникального ID в каждом правиле.
* Обеспечь предсказуемое поведение, если на странице присутствуют несколько экземпляров одной конфигурации.
* Подключай или выводи пользовательский CSS только при необходимости.
* Корректно обрабатывай сохранение и экранирование данных в административном интерфейсе.
* Не считай sanitize_text_field() универсальным способом очистки CSS: он может повредить синтаксис. Используй подходящую стратегию проверки, хранения и безопасного вывода CSS с учётом ограничений WordPress.
Пример желаемого поведения:
.title {
    color: red;
}
должен применяться только внутри соответствующей сетки, не затрагивая .title в других компонентах сайта.
Определи и реализуй чёткие правила изоляции CSS.
10. AJAX-фильтры
Реализуй фильтрацию результатов без полной перезагрузки страницы.
Минимальные возможности:
* Фильтрация по категориям портфолио.
* Фильтрация по тегам портфолио.
* Поддержка других таксономий, доступных выбранному источнику, если это реализуемо для данного типа данных.
* Возможность отключить фильтры для конкретной сетки.
* Настраиваемый интерфейс фильтров в рамках возможностей редактора.
Требования:
* После выбора фильтра обновляются результаты сетки.
* Полная страница не перезагружается.
* Новые результаты сохраняют выбранный тип макета и скин.
* При изменении фильтра текущая страница пагинации сбрасывается на первую.
* Фильтры должны работать вместе с AJAX-пагинацией.
* Данные запроса валидируются на сервере.
* Проверяется доступность запрошенного источника и выбранных таксономий.
* Состояние фильтров должно быть изолировано между разными экземплярами сеток на одной странице.
11. AJAX-пагинация
Создай полноценную AJAX-пагинацию с тремя режимами.
Режим 1: Disabled
Пагинация отключена.
Выводится только количество элементов, определённое настройками сетки, без элементов управления для перехода к следующим результатам.
Режим 2: Page Numbers
Отображается нумерация страниц.
При выборе другой страницы:
* Выполняется AJAX-запрос.
* Результаты текущего набора заменяются новыми.
* Полная страница не перезагружается.
* Сетка сохраняет текущий макет, скин и фильтры.
* Активный номер страницы обновляется.
* Повторное использование обработчиков событий не приводит к дублированию событий.
Режим 3: Load More
Отображается кнопка Load More.
При нажатии:
* Следующая порция элементов загружается через AJAX.
* Новые карточки добавляются в существующую сетку.
* Уже отображённые элементы не дублируются.
* Кнопка отключается или показывает состояние загрузки на время запроса.
* Если больше результатов нет, кнопка скрывается или заменяется понятным сообщением.
* Сохраняются текущие фильтры, макет и скин.
Общие правила
* AJAX-пагинация должна корректно работать вместе с Query Builder.
* Учитывай offset, количество элементов на странице и фактическое число найденных записей.
* Не показывай страницы, на которых нет результатов.
* Защищай серверные обработчики и валидируй параметры.
* Используй nonce там, где это уместно для конкретного сценария.
* Не считай nonce заменой проверке прав доступа.
* Предотвращай гонки запросов: устаревший ответ не должен перезаписывать более свежий результат после изменения фильтров.
* Не создавай повторные AJAX-обработчики при повторной инициализации.
* Не используй глобальные переменные, которые смешивают состояние нескольких сеток.
12. Shortcode
Для каждой сохранённой конфигурации должен автоматически поддерживаться шорткод вида:
[vlt_grid_builder id="123"]
Здесь 123 — ID записи Saved Layouts.
Требования
* При рендеринге шорткод загружает сохранённую конфигурацию.
* Все результаты формируются через единый Query Builder и Layout Engine.
* Работают выбранный макет, скин, фильтры и пагинация.
* Корректно обрабатываются отсутствующие, удалённые или недоступные конфигурации.
* Нельзя передать произвольный путь к файлу через атрибуты шорткода.
* Используй уникальный идентификатор для каждого экземпляра сетки.
* Поддержи несколько разных сеток на одной странице.
* По возможности поддержи повторное размещение одной конфигурации на странице без конфликтов JavaScript и CSS.
При необходимости можешь добавить дополнительные необязательные атрибуты, но базовый шорткод должен работать самостоятельно и не требовать ручного указания всех настроек.
13. Общая архитектура рендеринга
Создай единый поток обработки:
1. Шорткод или другой поддерживаемый способ вывода получает ID Saved Layouts.
2. Загружается и проверяется конфигурация.
3. Query Builder формирует запрос для выбранного источника.
4. Layout Engine определяет разметку Grid, Tiles или Masonry.
5. Система скинов подключает соответствующие шаблоны и ресурсы.
6. Результаты выводятся внутри изолированного контейнера.
7. JavaScript инициализирует фильтры и AJAX-пагинацию.
8. AJAX-запросы используют ту же серверную логику, что и первоначальный рендеринг.
Не создавай отдельные несовместимые механизмы для первоначальной загрузки и AJAX-обновления. Используй общие функции формирования запросов, проверки конфигурации и рендеринга результатов.

19. Критерии готовности
Задача считается выполненной, когда:
1. Все файлы модуля находятся внутри VLThemes-toolkit/includes/grid-builder/.
2. Модуль подключён к существующему VLThemes Toolkit и не требует установки отдельного плагина.
3. Portfolio Items и Saved Layouts доступны в админке.
4. Конфигурации сеток можно создавать, сохранять и редактировать.
5. Query Builder формирует реальные запросы к выбранным источникам.
6. Grid, Tiles и Masonry действительно работают.
7. Tiles использует валидируемую конфигурацию композиции.
8. Masonry не использует стороннюю библиотеку или JS-расчёт координат.
9. Скины обнаруживаются автоматически, а Default и Fade работают.
10. Пользовательский CSS изолирован для соответствующей сетки.
11. AJAX-фильтры работают без полной перезагрузки страницы.
12. Все режимы пагинации работают через AJAX.
13. Шорткод выводит сохранённую конфигурацию.
14. Несколько сеток на одной странице не конфликтуют.
15. Код проверен настолько, насколько позволяет доступное окружение.
16. Не осталось фиктивных кнопок, демонстрационных заглушек или незавершённых ключевых функций.
